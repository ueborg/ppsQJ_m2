# Ruche runbook — the commands, for the human to type

**No agent submits any of this.** `research/RESOURCE_POLICY.md` §4 forbids it
unconditionally, at every stage and gate. Nothing in this package contains an
executable scheduler call; `preflight.py` asserts that about `run_preflight.sh`
and fails if it stops being true.

Three arrays, 288 tasks, ~61 core-hours, ~1 h elapsed for the long pole
excluding queue wait.

## 2. Check your queue accounting first

The cost model assumes `%64` grants 64 concurrent slots **per array**. On
2026-09-02 the predecessor's ARM B demonstrated that on `cpu_med`, with three
arrays live at once. Confirm it still holds for your allocation before relying
on the elapsed-time figures:

```bash
# what the account is allowed
sacctmgr show assoc where user=$USER format=Account,Partition,GrpTRES,MaxJobs,QOS

# what the QOS actually caps
sacctmgr show qos format=Name,MaxJobsPU,MaxSubmitPU,MaxTRESPU
```

- If slots are granted **per array**: leave `%64` alone.
- If they are shared **in total across all three arrays**: lower `%64` to `%21`
  in each `submit.slurm`. **The `%N` cap is the only number in these scripts
  that is safe to hand-edit**; everything else is regenerated by
  `tools/build_arms.py` and the preflight will fail if you touch it.
- If `cpu_med` itself turns out to be QOS-limited for this account, **stop and
  report it**. Do not fall back to `cpu_short` — that would make the campaign's
  parallelism assumption wrong everywhere in the programme, not just here, and
  it is worth knowing rather than working around.

## 7. Completeness check

```bash
for arm in lowlamL32 lowlamL48 lowlamL64; do
    n=$(find $arm/results -maxdepth 1 -name '*.json' | wc -l | tr -d ' ')
    echo "$arm  $n / 96"
done

# any task that failed
grep -l . lowlam*/logs/*.err 2>/dev/null | head
```

96 per arm, 288 total. Re-running `sbatch submit.slurm` is safe and idempotent:
`run_cell.py` skips a row whose output JSON already exists, so a partial array
can be topped up without recomputing anything.

## 9. The analysis

**One command. It is the only place the frozen criteria are evaluated.**

```bash
cd /Users/catlover1337/Documents/ppsQJ_m2
.venv/bin/python3 \
  research/tasks/active/TASK-2026-09-03-MOCK-LOWLAMBDA-EXTENSION/analysis/lowlambda_analysis.py \
  | tee research/tasks/active/TASK-2026-09-03-MOCK-LOWLAMBDA-EXTENSION/LOWLAMBDA_ANALYSIS.txt
```

It writes `LOWLAMBDA_RESULTS.json` and three figures under `analysis/figures/`,
and prints:

- the 17-point curves at `L = 32, 48, 64` with across-population SEMs;
- the full curve-quality battery, plus the 13 old points recomputed alone as a
  reuse check;
- per-cell split-half, outlier and leave-one-out diagnostics;
- **the join tests J1, J2, J3** at each `L`;
- **the crossing analysis on all three pairs**, with the interiority
  classification `INTERIOR` / `STILL_BOUNDARY` / `BELOW_GRID` / `NONE`;
- the pre-registered criteria X1–X7.

It runs to completion with zero, partial or complete results and says which.

Then, and only then, write `FALSIFICATION_RESULTS.md` against the frozen
`FALSIFICATION_PLAN.md`. **The plan is frozen; the results are a different
file.** Do not edit the plan to match what happened.

fresh task, a fresh justification that is not "the last one didn't work", and a
