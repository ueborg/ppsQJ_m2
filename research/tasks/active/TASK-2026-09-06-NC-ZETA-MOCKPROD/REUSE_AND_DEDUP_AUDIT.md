## 1. Method

`[E]` The scan reads `research/tasks/**/results/*.json` — **stored populations**,
not manifest rows. A manifest row that was cancelled or never returned cannot be
counted as existing data. This is the failure `NC-ZETA-CALIBRATION` corrected
when it found `D_L128_nc2048/results/` empty while the design assumed a rung
there.

`[E]` A cell is the seven-tuple
`(zeta, L, T, N_c, lambda, dtau_mult, resample_scheme)`. Three classes:

| class | meaning |
|---|---|
| `EXACT` | identical to a cell this task would run — running it would be a **duplicate** |
| `ADJACENT` | same `zeta`, a cell this task does not run |
| `INCOMPATIBLE` | different `zeta`, or a non-production configuration |

## 2. Result

```
populations scanned       : 5 185
distinct cells            : 136
cells this task would run : 407   (405 production + 2 discretisation control)
EXACT-compatible existing : 0 populations in 0 cells
ADJACENT (same zeta)      : 0 populations
zeta present in corpus    : 0.05, 0.30, 0.35, 0.70
```

`[E]` **There is nothing to reuse.** Not one stored population matches any cell
this task would run, and not one matches even the `zeta` values at a different
`lambda` or `N_c`.

`[E]` **`zeta = 0.70` appears in the corpus and is still not reusable.** The nine
rows outside `zeta = 0.35` are `TASK-2026-08-11-ALGRD` and
`TASK-2026-08-11-ARCH` architecture benchmarks: one JSON per *arm*, not per
population, `N_c in {44, 88, 175, 300, 350, 500}`, no `resample_scheme` field, and
`dtau_mult` absent from the record. `[I]` They are timing and architecture
artifacts. Pooling them with production cells would be exactly the silent
contamination the matched-`R` rule exists to prevent, and the classifier marks
them `INCOMPATIBLE` on the `resample_scheme` and `dtau_mult` fields before `zeta`
is even considered.

## 3. `zeta = 0.35` is not recomputed

`[E]` Brief §9 forbids it and no arm contains it. The
`tools/no_zeta035.py` negative control asserts that the string `0.35` does not
appear in the `zeta` column of any manifest this task ships, and the preflight
runs it.

`[E]` The `zeta = 0.35` **reference row** in the final tables is quoted from
`TASK-2026-09-03-MOCK-LOWLAMBDA-EXTENSION` — `L48-L64` rough crossing `0.23691`,
`N_c = 1024`, `R = 24`, 17-point grid, `INTERIOR` — and is labelled as a quoted
predecessor measurement at a **different `R` and a different `lambda` grid**. It
is a reference point, never a row this task measured, and never pooled into any
statistic computed here.

## 4. Historical `sqrt(zeta)`-centred scans

`[E]` Used **only** as descriptive context in `LAMBDA_GRID_DECISION.md` §4, to
check that a wide bracket is sensible, and in `COST_MODEL.md` §4 for the
`zeta` timing ratios, where only the ratio at fixed `L` is used and the absolute
level always comes from the Ruche table.

`[E]` They are **not evidence for a `sqrt(zeta)` law** and no grid in this task
is centred on one. The grids are centred on nothing: they are constructed to
span both open positions of `DISP-PHI-001` plus margin, which is the property
`NC-ZETA-CALIBRATION`'s preflight check `P9` failed to test.

## 5. Duplication against sibling tasks

`[E]` `tools/dedup_scan.py` re-derives the same conclusion independently by
scanning every `manifest.csv` under `research/tasks/` — including this task's
own arms — and failing on any repeated
`(zeta, L, T, N_c, lambda, dtau_mult, resample_scheme, seed)` or any repeated
seed. It is a hard preflight failure, not a note.

## 6. The one internal reuse

`[E]` The discretisation control (brief §8) needs `dtau_mult in {3, 6, 12}` at
`L = 64`, `N_c = 512`, `zeta = 0.10`, `lambda = 0.100`. The `dtau_mult = 6` leg
**already exists inside this task's own main arm** `M_z010_nc512`, at the same
`R = 16` and the same seeds' block, because `lambda = 0.100` is an on-grid point.
`[E]` The control arm therefore ships only the `dtau_mult = 3` and `12` legs —
32 populations instead of 48 — and `ANALYSIS_SPEC.yaml` records the resulting
**submission dependency**: the control cannot be analysed until `M_z010_nc512`
has returned. `[J]` Saving 16 populations is not the point; running the
`dtau_mult = 6` leg twice under two different seed blocks and then comparing them
as if they were one measurement is.
